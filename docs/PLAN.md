## 0. Что в исходной постановке кривое

### 0.1. Ниша, которую ты описал, уже занята

Ты позиционируешь проект как «open-source локальный инструмент под MCP, ниша **под** энтерпрайзом». Эта ниша не пустая:

- **mcp-scan** (Invariant Labs, куплены Snyk) — статический сканер + **динамический прокси**, который встаёт в путь трафика, логирует и применяет guardrail'ы к вызовам тулов в реальном времени. У них уже есть **tool pinning через хэширование** — ровно защита от rug pull / MCPoison-класса. Плюс детект tool poisoning, cross-origin escalation (tool shadowing) и анализ «toxic flows».
- **Lasso MCP Gateway** — открытый security-ориентированный MCP-гейтвей, выложен ещё в апреле 2025.
- Оркестраторы (IBM ContextForge, Docker MCP Gateway, Microsoft MCP Gateway, MCPJungle, Bifrost) — это не про угрозы, а про федерацию/RBAC/аудит, но они занимают слово «gateway».

**Что это меняет:** не концепцию, а нарратив и приоритеты. Ты не первый. Строить «ещё один» имеет смысл только если ты явно отвечаешь, чем ты другой. Живые ответы:

1. **Один статический бинарник, ноль зависимостей, ноль сетевых вызовов.** mcp-scan — Python (pip/uv), и его лучший детект исторически завязан на облачный Guardrailing API; локальный режим требует ключа OpenAI. Полностью офлайновый, детерминированный, no-API-key инструмент — это реальная дыра, и она ровно под твои навыки.
2. **Прокси не переписывает чужие конфиги.** mcp-scan временно инжектит себя в конфиги MCP-серверов и убирает после выхода. Это архитектурно стрёмно (гонки, падение на середине, битый конфиг). Ты — обёртка, которую юзер прописывает руками один раз.
3. **Честный README со сравнением.** «Я прочитал исходники mcp-scan, вот что сделал иначе и почему» — это сильный сигнал на собесе. Сильнее, чем делать вид, что ты первый.

**Что сделать в первую неделю (до кода):** поставить mcp-scan, прогнать `scan` и `proxy` на своих серверах, прочитать их код прокси. Один вечер. Ты либо найдёшь, что делать иначе, либо поймёшь, что делать не надо. Оба исхода дешевле, чем три месяца вслепую.

### 0.2. Угроза №2 (подмена конфига) в прокси не лечится

Твой прокси **прописан в том самом конфиге**, который он охраняет. Кто может переписать `mcp.json`, тот первой строкой выпиливает `mcp-guard` из цепочки. Круг замкнулся.

Значит:

- ConfigGuard — это **отдельный компонент**, не часть пути трафика: `mcp-guard watch` (inotify/fsnotify на конфиги клиентов) + `mcp-guard verify` (pre-flight проверка).
- Эталон хранится **вне** директории конфига и в идеале в git репозитория проекта, а не в `~/.config`.
- Прокси может дополнительно отказываться стартовать при несовпадении хэша — но это второй рубеж, а не первый.

Это не значит «не делай». Это ~200 строк и отличная быстрая победа для демо. Просто не выдавай её за архитектуру.

### 0.3. Главное: ты выбрал самый слабый рычаг главным

«Определить, является ли текст prompt injection» — задача с фундаментально плохим потолком. Не потому что regex слабый (он слабый), а потому что в MCP инструкция и данные — это **буквально одна и та же сущность**. Строка «удали все временные файлы» в письме — это данные или команда? Ответ зависит от того, как агент решит её прочитать, а не от самой строки. Никакой классификатор — ни regex, ни LLM — не имеет доступа к этому решению.

Практическое следствие: FP-рейт будет чудовищный. Читаешь блог-пост про prompt injection — сработка. Ревьюишь код с комментарием `// ignore the above` — сработка. Юзер сносит инструмент через два дня.

**Инверсия, на которой надо строить продукт:**

> Не классифицируй контент. Контролируй эффекты.

CurXecute остановился бы не на «мы разглядели инструкцию в сообщении Slack», а на «агент попытался записать в `~/.cursor/mcp.json` — не дали». Это детерминированно, это тестируемо, у этого измеримый FP, и это не обходится перефразировкой.

Архитектурно это значит: ядро — **политика над вызовами тулов** (эгресс), а контентная инспекция — это **taint-маркер**, который поднимает уровень политики, а не блокирует сам по себе.

Механика taint:

- Пометить сессию как «загрязнённую», когда результат тула пришёл из недоверенного источника: HTTP-fetch, почта, issue tracker, Slack, чужой репозиторий, шаренная ФС.
- В загрязнённой сессии правила ужесточаются: то, что было `allow`, становится `confirm`; запись в чувствительные пути и любой `exec` — жёсткий блок или явное подтверждение.
- Решение принимается по **источнику и эффекту**, не по формулировке. Атакующему надо достичь эффекта, а множество опасных эффектов конечно и мало.

Побочный бонус: taint-трекинг + capability-политика — это системная тема (потоки данных, привилегии, канонизация путей). Для нарратива «ищу стажировку в системном программировании» это в разы лучше, чем «написал детектор на регулярках».

### 0.4. Мелочь: не называй это Gateway

Слово занято энтерпрайз-оркестраторами, тебя будут сравнивать не с тем. `mcp-guard`, `mcpwatch`, что угодно без «gateway».

## 1. Архитектурные развилки

### 1.1. Где сидит прокси

| Вариант | Вердикт |
|---|---|
| **stdio-обёртка**: клиент запускает `mcp-guard -- npx -y @mcp/server-filesystem /home/u`, guard форкает настоящий сервер | **Да, только это в v1** |
| HTTP / SSE / Streamable HTTP reverse proxy | Этап 5, если вообще |
| Агрегирующий прокси (один MCP-сервер, который сам клиент ко всем остальным) | **Нет** |

Почему только stdio: подавляющее большинство локальных серверов у Claude Code и Cursor — stdio. Агрегатор ломает namespace тулов, убивает per-server capability negotiation, создаёт единую точку отказа и уже нормально сделан у Bifrost/ContextForge — там ты не выиграешь. HTTP добавляется дёшево (`httputil.ReverseProxy` + разбор тела), но SSE-стриминг ломает построчный разбор и требует отдельного парсера событий — не в v1.

### 1.2. Как перехватывать stdio и не сломать клиента

Ты — прозрачный ретранслятор JSON-RPC 2.0, newline-delimited (в сообщении не бывает `\n`). Правила, нарушение каждого = баг-репорт от юзера:

- **stderr не глотать.** Сервера логируют туда, клиенты это показывают. Проксируй 1:1.
- **Не буферизовать.** Write + flush на каждое сообщение. Иначе получишь «клиент завис на 30 секунд».
- **Не дропать сообщения.** Если блокируешь — обязан синтезировать валидный ответ с **тем же `id`** и внятным текстом ошибки. Иначе клиент виснет до таймаута и юзер не понимает, что произошло.
- **Тело держать в `json.RawMessage`.** Не размаршаливай-ремаршаливай ради удовольствия: байты должны доходить как есть (важно для хэширования и для отладки).
- **Трафик двунаправленный.** Сервер тоже шлёт запросы клиенту: `sampling/createMessage`, `roots/list`, `elicitation/create`. Парсер обязан уметь обе стороны и различать request / response / notification.
- **Batching.** В ревизии 2025-03-26 был JSON-RPC batch (массив на верхнем уровне), в 2025-06-18 убрали. Поддержи оба — увидишь на старых серверах.
- **Lifecycle.** Клиент закрыл stdin → ты закрываешь stdin ребёнку → ждёшь выхода с таймаутом → SIGTERM → SIGKILL. Иначе зомби-`npx` будут копиться до перезагрузки.
- **`bufio.Scanner` дефолтно ломается на 64 KB.** Ответы тулов легко больше. `scanner.Buffer(make([]byte, 0, 64*1024), 16<<20)` или `bufio.Reader.ReadBytes('\n')`. Это первый баг, на который ты напорешься, и он выглядит как «сервер молча отвалился».

### 1.3. Дочерние процессы

Ты сам родитель — это преимущество, а не проблема. Можешь фильтровать окружение (не пробрасывать `AWS_*`, `GITHUB_TOKEN`, `*_API_KEY`, если политика не разрешает), выставлять cwd, ставить rlimits. Namespaces/seccomp — не трогай, это уже делает Docker MCP Gateway контейнерами, и делает лучше.

### 1.4. Как спрашивать подтверждение у юзера

В stdio у тебя нет UI. Варианты по убыванию красоты:

1. **`elicitation/create` от прокси к клиенту** — протокольно родной способ, клиент сам рисует диалог. Требует поддержки клиентом (ревизия 2025-06-18+). Проверь на Claude Code до того, как закладывать в дизайн.
2. Fallback: блок + понятная ошибка в теле ответа тула + запись в аудит + `notify-send`/`osascript`.
3. **Не строй TUI и не строй веб-панель.** Оба варианта съедят месяц и не добавят безопасности.

## 2. Язык и стек

**Пиши сразу на Go. Не делай v0 на Python.**

Аргументы, а не «зависит от тебя»:

1. **Дистрибуция здесь — это половина продукта.** Твой артефакт — строчка в чужом `mcp.json`. Юзер должен скачать один файл и указать путь. Python = pip/uv/venv/версия интерпретатора/конфликт с системным. Один статический бинарник — это не «приятнее», это разница между «поставили» и «забили после первого `ModuleNotFoundError`».
2. **Ты знаешь C.** Go после C заходит за неделю. И конкретно этот проект не требует ничего сложного: три пайпа, JSON, горутины, `context`. Никаких дженериков-акробатики, никаких фреймворков.
3. **«Сделаю на питоне, потом перепишу» — это ложь, которую ты себе рассказываешь.** К моменту, когда питон-версия работает, у неё уже тесты, юзеры и хвост фич. Переписать 5к строк на незнакомом языке в одиночку по вечерам — это не «две недели», это смерть проекта. Переписывания не случаются.
4. **Портфолио.** Ты метишь в C++/системку. «Написал прокси, разобрал бинарный лайфцикл процессов, реализовал протокол» на Go читается как системная работа. Тот же код на Python читается как скрипт.
5. **Единственный контраргумент — официальный Python SDK — тут не работает.** Тебе SDK не нужен: ты не пишешь MCP-сервер, ты ретранслируешь байты. SDK абстрагирует ровно тот слой, на котором ты работаешь, и будет мешать.

**Цена решения:** +30–50% времени на первые три недели. Плати, это разовый платёж.

**Питон-прототип не выбрасывай.** Он становится:
- источником правил (вынеси regex в YAML — правила должны быть данными, а не кодом);
- reference implementation для сверки: один и тот же корпус через обе реализации, результаты должны совпадать.

**Стек:** только stdlib + минимум. `encoding/json`, `os/exec`, `bufio`, `context`, `log/slog`. Из внешнего максимум: `gopkg.in/yaml.v3` (политики), `github.com/fsnotify/fsnotify` (watch), `github.com/bmatcuk/doublestar` (glob по путям). Всё. Каждая новая зависимость в security-инструменте — это твоя же supply chain.

**Что учить в Go именно под это (не проходи курс, учи по задаче):**
Tour of Go за вечер → дальше сразу код. Нужно ровно: горутины + каналы (три пайпа), `context` для отмены, `os/exec` со `StdinPipe`/`StdoutPipe`/`StderrPipe`, `json.RawMessage`, `errors.Is/As`, table-driven тесты. Читай исходники stdlib, а не туториалы.

## 3. Этапы

Расчёт: ~10–12 часов в неделю (вечера + выходные). Плюс налог на изучение Go в первые 3 недели.

### Этап 0 — «Прозрачная труба» (1 вечер, ~150 строк)

Прокси, который **ничего не проверяет**. Форкает реальный сервер, гоняет stdin/stdout/stderr насквозь, попутно пишет каждое сообщение в `session.jsonl` с меткой направления и времени.

**Готово, когда:** Claude Code работает через `mcp-guard --` абсолютно так же, как без него (тулы видны, вызовы проходят, ошибки видны), а в логе лежит полная сессия: `initialize` → `initialized` → `tools/list` → `tools/call`.

Это не разминка. Это фундамент: **сбор benign-корпуса начинается прямо здесь**, с первого вечера. Через два месяца у тебя будет реальный корпус нормального трафика, на котором меряется FP. Без него весь детект — гадание.

### Этап 1 — «Протокол, а не байты» (1.5–2 недели)

- Полноценный разбор JSON-RPC: request / response / notification / error, обе стороны.
- Корреляция request↔response по `id`, с таймаутами и очисткой висяков.
- Модель сессии: версия протокола, capabilities, список тулов, история вызовов.
- Корректный teardown (см. 1.2).
- `mcp-guard replay session.jsonl` — человекочитаемый транскрипт сессии.

**Готово, когда:** `replay` даёт читаемую расшифровку любой записанной сессии; убийство дочернего сервера даёт чистое завершение без зомби; **conformance-тест на прозрачность** проходит — прогон одной и той же сессии с guard и без него даёт идентичные последовательности сообщений.

Этот conformance-тест — твой главный регресс. Пиши его сейчас, он спасёт тебя на этапе 3.

### Этап 2 — «Пиннинг» (2 недели)

- `mcp-guard approve` → `mcp-guard.lock`: хэши команды сервера, argv, **ключей** окружения (не значений!), и для каждого тула — `name` + `description` + канонизированный `inputSchema`.
- **Канонизация JSON обязательна** (рекурсивная сортировка ключей, нормализация чисел; либо RFC 8785 JCS). Иначе сервер переставит поля в схеме и ты получишь FP на ровном месте.
- Сверка при каждом `tools/list` и перед каждым `tools/call`. Несовпадение → блок с внятной ошибкой + предложение `mcp-guard approve --diff`.
- Отдельно: `mcp-guard watch` — fsnotify на конфиги клиентов, эталон вне директории конфига.
- Локфайл кладётся в git репозитория → изменения тулов видны в диффе на код-ревью. Это отдельный кайф и сильный аргумент в README.

**Готово, когда:** сценарий MCPoison (тихая подмена после апрува) блокируется, клиент показывает осмысленную ошибку, `--diff` показывает, что именно изменилось.

### Этап 3 — «Политика эффектов + taint» (3 недели) ← ядро продукта

- Файл политики (YAML): правила `allow` / `confirm` / `deny` по имени тула + паттернам аргументов.
- **Канонизация путей — самая злая часть.** Резолвить `~`, `..`, симлинки, относительные пути, регистр на macOS, unicode-нормализацию. Проверять после резолва. Дефолтный чувствительный набор: `~/.ssh`, `~/.aws`, `~/.gnupg`, `**/.git/hooks/**`, `**/mcp.json`, `**/.cursor/**`, `**/.claude/**`, `~/.bashrc`, `~/.zshrc`, `**/.env`, systemd user units, autostart.
- Отдельный класс: любой тул с shell/exec-семантикой.
- Taint: помечать сессию, когда результат пришёл от тула из категории «внешний контент» (fetch, почта, issues, Slack, чужие репы). Категория задаётся в политике, по имени/серверу.
- Эскалация: в загрязнённой сессии `allow` → `confirm` для чувствительных эффектов.
- Механизм подтверждения (см. 1.4).

**Готово, когда:** сценарий CurXecute блокируется **на записи**, а не на распознавании текста; при этом прогон всего benign-корпуса даёт ноль блокировок.

Вторая половина критерия важнее первой.

### Этап 4 — «Контентные сигналы и метрики» (2 недели)

- Правила из питон-прототипа → в YAML.
- **Пасс нормализации перед матчингом** — тут дешёвый двукратный выигрыш: декод base64/hex, вырезание zero-width и unicode-гомоглифов, извлечение HTML-комментариев и `display:none`, разворачивание URL-энкодинга.
- Выход детектора — **score, а не блок**. Score поднимает taint-уровень. По умолчанию контент ничего не блокирует. Никогда.
- Харнесс метрик: `mcp-guard eval --attack corpus/attack --benign corpus/benign --policy p.yml`.

**Готово, когда:** есть цифры: recall на attack-корпусе, FP per rule на benign, и «блокировок за неделю нормальной работы».

### Этап 5 — опциональное (не планируй заранее)

HTTP/SSE-транспорт. LLM-классификатор (только opt-in, только на уже загрязнённых сессиях перед чувствительным эффектом, с кэшем по хэшу контента). Sandboxing дочерних процессов.

**Итого до полезной v0.3: ~2.5–3 месяца.** Это честно при вечерах, а не «за месяц накидаю».

## 4. Стратегия детекта: порядок по отдаче

По убыванию пользы на вложенный час:

1. **Пиннинг схем тулов** — детерминированно, FP = 0 при правильной канонизации, закрывает целый опубликованный класс атак.
2. **Политика эффектов по путям и exec** — детерминированно, FP управляем списком.
3. **Taint-эскалация** — решение по источнику, а не по формулировке. Не обходится перефразировкой.
4. **Нормализация + сигнатуры** — только advisory.
5. **LLM-классификатор** — дорого, медленно, недетерминированно, требует ключа. Последним и опционально.

**Где regex перестаёт окупаться:** сразу. Он не должен блокировать **никогда**. Твои правила лежат в открытом репозитории — обход занимает у атакующего тридцать секунд. Ценность regex как защиты близка к нулю; как телеметрии и как входа в taint — ненулевая. Держи его ровно в этой роли и не соблазняйся «ну ещё пять паттернов и заработает».

Структурный анализ (парсинг разметки, детект инструкций в невидимых зонах) — стоит того, но именно как часть нормализации на этапе 4, а не как отдельная подсистема.

## 5. Тестирование

### Два корпуса, и второй важнее

**Attack-корпус** — опубликованные PoC: tool poisoning и tool shadowing от Invariant, CurXecute (запись в `.cursor/mcp.json` через подброшенное сообщение), MCPoison (тихая подмена после апрува), git-hook сценарий. Плюс свои.

**Benign-корпус** — твои реальные сессии, записанные с этапа 0. Filesystem, git, fetch, твоя учебная работа, Claude Code за реальными задачами. **Это единственный источник правды по FP**, и его нельзя выдумать.

### Инфраструктура

- **`testdata/evil-server/`** — свой злонамеренный MCP-сервер как фикстура. Лучше захардкоженных строк: проверяет весь путь, а не кусок парсера.
- **Реплей-харнесс.** Всё гоняется по `.jsonl` без живых серверов: быстро, детерминированно, идёт в CI.
- **Golden-файлы** на решения политики: `input.jsonl` + `expected-verdicts.json`.

### Метрики

- Recall на attack-корпусе.
- FP rate **по каждому правилу** на benign — чтобы видно было, какое правило тащит вниз.
- **«Блокировок за неделю нормального использования».** Единственная метрика, которая предсказывает, снесут инструмент или нет. Цель: меньше одной. Выноси её в README.

### Режимы

Дефолт при установке — **observe**, не enforce. Юзер неделю смотрит, что бы заблокировалось, потом сам включает enforce. Инструмент, который на первый день ломает рабочий процесс, удаляют на первый день.

## 6. Чего НЕ делать

**Никогда в v1:**
- Веб-панель, дашборд, графики.
- Плагинная система, Lua/WASM/скриптовый движок правил.
- Локальные ML-модели, эмбеддинги, векторные базы.
- Мультитенантность, RBAC, авторизация, аккаунты.
- Облако, телеметрия, «анонимная статистика».
- **Молчаливая санитизация контента.** Незаметно править ответ тула хуже, чем блокировать: ты ломаешь корректность работы агента невидимо для юзера. Только блок + явное сообщение.

**По этапам:**
- Э0–1: не трогай детект вообще. Ни одного правила. Только труба и парсер.
- Э2: не пиши политику. Только пиннинг.
- Э3: не трогай контент. Только эффекты и taint.
- Э4: не добавляй LLM. Только нормализация и метрики.

**Отложи до появления настоящих юзеров:** HTTP/SSE, агрегация серверов, sandbox дочерних процессов, поддержка Windows-специфики, интеграции с CI, signed rules.

**И отдельно:** не расширяй список классов угроз. Три — уже много. Четвёртый класс = ещё месяц и ноль дополнительной ценности.

## 7. Первый вечер: что конкретно писать

```
mcp-guard/
├── go.mod
├── cmd/mcp-guard/main.go
├── internal/proxy/proxy.go
└── README.md
```

Задача одна: `mcp-guard --log ~/.mcp-guard/session.jsonl -- npx -y @modelcontextprotocol/server-filesystem /home/user/tmp`

Скелет (намеренно неполный — дописывай сам, тут смысл в форме):

```go
func Run(ctx context.Context, argv []string, logw io.Writer) error {
    cmd := exec.CommandContext(ctx, argv[0], argv[1:]...)
    stdin, _ := cmd.StdinPipe()
    stdout, _ := cmd.StdoutPipe()
    cmd.Stderr = os.Stderr // прокидываем как есть, не глотаем

    if err := cmd.Start(); err != nil {
        return err
    }

    var wg sync.WaitGroup
    wg.Add(2)
    go func() { defer wg.Done(); pump("c2s", os.Stdin, stdin, logw) }()
    go func() { defer wg.Done(); pump("s2c", stdout, os.Stdout, logw) }()
    wg.Wait()
    return cmd.Wait()
}

func pump(dir string, src io.Reader, dst io.Writer, logw io.Writer) {
    r := bufio.NewReaderSize(src, 1<<20)
    for {
        line, err := r.ReadBytes('\n')   // НЕ Scanner: 64KB лимит убьёт на большом ответе
        if len(line) > 0 {
            fmt.Fprintf(logw, `{"t":%q,"dir":%q,"msg":%s}`+"\n",
                time.Now().Format(time.RFC3339Nano), dir, bytes.TrimSpace(line))
            dst.Write(line)
            if f, ok := dst.(interface{ Sync() error }); ok {
                f.Sync()   // без флаша клиент будет висеть
            }
        }
        if err != nil {
            return
        }
    }
}
```

**Критерий вечера:** прописал в `~/.claude.json` (или конфиг Cursor) обёртку вместо прямого запуска сервера → Claude Code видит тулы → вызвал тул → в `session.jsonl` лежат `initialize`, `tools/list`, `tools/call` с обеих сторон.

Всё. Никакого детекта, никакого парсинга JSON сверх записи в лог. Если в первый вечер захочется добавить «ну хоть одну проверку» — не добавляй, это ровно тот преждевременный уход в сложность, про который ты сам написал.
