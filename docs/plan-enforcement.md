# Включить защиту: градуированный enforce, аварийный выключатель и починка гейта

## Контекст

Все четыре этапа плана закрыты, mcp-guard работает и пишет корпус, но **живёт только в режиме observe**. Включить `--enforce` сегодня нельзя по двум причинам.

Первая — поведенческая. Enforce сейчас всё-или-ничего: `deny` и `confirm` принуждаются одним и тем же флагом. В deny-списке ключи, конфиги агента и startup-файлы — туда нормальная работа не пишет никогда. В confirm-списке `package.json`, `pyproject.toml`, а под taint ещё `*.sh`, `Makefile`, `.github/workflows` — в них пишешь постоянно. Жёсткий отказ по ним ломает работу в первый же день, а по плану метрика «блокировок в неделю» — единственная, предсказывающая, снесут инструмент или нет. Протокольный способ спросить подтверждение закрыт: проверено по корпусу, клиент не объявляет `elicitation` (только `roots` и UI-расширение).

Вторая — баги, из-за которых включение защиты опасно само по себе:

- `pendingTools` течёт: запись делается до решения об отказе и для отказанных вызовов не удаляется никогда. Второй путь утечки — любой потерянный ответ: `answered()` вызывается только при совпадении в корреляторе, а у карты гейта нет подметальщика.
- Пакетные фреймы обходят гейт целиком. Заодно результаты пакетных вызовов никогда не поднимают taint.
- Ошибка `Lock.Verify` оставляет старую карту несовпадений — fail-open по пиннингу.
- `refuse` возвращает `nil` при ошибке маршалинга, а `nil` означает «пропустить».
- Отказанный вызов не попадает в модель сессии: транскрипт врёт после каждой блокировки.

**Цель:** сделать `--enforce` тем, что можно включить и оставить включённым.

## Решения, принятые заранее

| | |
|---|---|
| `confirm` при enforce | пропускается, но громко фиксируется. Блокирует только отдельный строгий уровень |
| Аварийный выключатель | `MCPGUARD_OFF=1` → чистая труба |
| `elicitation` | вне объёма; capabilities начинаем захватывать и логировать |

## Три уровня, один словарь

В `internal/policy/policy.go`:

```go
const (
    Observe Mode = "observe" // записывать, пропускать всё
    Enforce Mode = "enforce" // deny блокирует; confirm фиксируется и пропускается
    Strict  Mode = "strict"  // confirm тоже блокирует
)

func ParseMode(s string) (Mode, error) // observe|off · enforce|deny · strict|all
func (m Mode) Blocks(a Action) bool    // ЕДИНСТВЕННОЕ место, где живёт градация
func (m Mode) Enforcing() bool
```

`Blocks` вызывает только guard; больше никто градацию не переизобретает.

**Комбинирование: командная строка главнее файла.** `resolveMode(flag, policy) (Mode, source)` — если флаг задан, побеждает флаг; иначе `mode:` из политики; иначе observe. Сегодня они OR-ятся, то есть политика умеет только повышать и спуститься нельзя не редактируя файл. Это меняется намеренно: локфайл политики предназначен для коммита и может быть чужим, а разбирается с поломкой в девять утра тот, у кого свой конфиг клиента.

**Флаг остаётся один.** `-enforce` становится `flag.Value` с методом `IsBoolFlag() bool` — стандартная библиотека это специально поддерживает, поэтому голое `-enforce` продолжает работать, а `-enforce=strict` и `-enforce=off` добавляются. Ловушка: `-enforce strict -- server` разберётся как `-enforce` плюс позиционный аргумент, то есть молча запустит сервер с именем `strict`. Пять строк проверки после `flag.Parse()` и внятная ошибка «используй `-enforce=strict` через знак равенства».

`Options.Enforce bool` **удаляется**, не устаревает — заменяется на `Mode policy.Mode`. Два поля, способных разойтись, это способ вернуть этот же баг.

## Этап A — фундамент

**`internal/policy/policy.go`** — `Strict`, `ParseMode`, `Blocks`, `Enforcing`; `strict` принимается в `Parse`.

**`internal/mcp/message.go`** — `NewError` теряет возврат ошибки (маршалинг строки не может упасть; при невозможном отказе подставляется фиксированное сообщение). Это убирает fail-open в `refuse`. Добавляется:

```go
// NewErrorBatch отвечает на пакетный фрейм пакетом: по ошибке на каждый id,
// в порядке поступления. Клиент, приславший массив и получивший объект,
// не сможет сопоставить ответ.
func NewErrorBatch(ids []ID, code int, message string) []byte
```

Правится единственный внешний вызов в `internal/probe/probe.go:190`.

**`internal/mcp/session.go`** — обе ветки рукопожатия уже разбирают анонимные структуры, добавляется `Capabilities json.RawMessage`. Плюс:

```go
type Capabilities struct { Raw json.RawMessage; Names []string }
func (s *Session) Capabilities() (client, server Capabilities)
func (s *Session) ClientSupports(name string) bool

// ObserveRefusal вносит в сессию вызов, на который прокси ответил сам.
// Коррелятор намеренно не трогается: ответа от сервера не будет, и запись
// в нём могла бы только протухнуть как ложный «без ответа».
func (s *Session) ObserveRefusal(dir Direction, request Message, reason string)
```

`mcp.Call` получает `Blocked bool` и `BlockReason string`.

## Этап B — корректность гейта

**`internal/proxy/guard.go`.** Структура получает `session`, `notice func(string, ...any)`, `now func() time.Time` (для тестируемого TTL, по образцу `mcp.Correlator`), счётчики `blocked`/`relayed`, карту `announced` для дедупликации сообщений, и `pendingTools map[string]pendingCall` со временем.

```go
func (g *guard) blocks(a policy.Action) bool { return g.o.Mode.Blocks(a) }

// expire выбрасывает привязки старше ttl. Без этого карта растёт всю сессию
// на каждом потерянном ответе — ровно то, ради чего у коррелятора есть
// подметальщик, только на одну карту в стороне.
func (g *guard) expire(ttl time.Duration) int
```

**`gate` разделяется на «рассудить» и «зафиксировать»** — починка пакетов и починка утечки это один и тот же рефакторинг:

```go
func (g *guard) inspect(m mcp.Message) gateResult // судит, но НЕ пишет в pendingTools
func (g *guard) gate(frame []byte) []byte
func (g *guard) refuseBatch(msgs []mcp.Message, reason string) []byte
```

Пакет судится целиком: если хоть один член отказан — отказывается **весь фрейм** через `NewErrorBatch`, и не запоминается ничего. Вырезать один член нельзя: в ответном массиве сервера образуется дыра на месте id, которого клиент ждёт, а сшивать свою ошибку с ответом сервера — это машина переписывания ответов ради фичи, убранной из протокола в ревизии 2025-06-18.

`refuse` записывает синтетический ответ в лог **до** отправки и зовёт `ObserveRefusal`. Порядок важен: если запись клиенту потом не удастся, лог честно говорит «отказали, клиент не получил».

**Пиннинг градуируется по виду сигнала:**

| сигнал | класс | почему |
|---|---|---|
| `ToolChanged` / `ToolAdded` | deny | срабатывает только когда инструмент реально изменился с момента твоего апрува. Редко, точно, с готовым лекарством в тексте отказа. Мягкость к `ToolAdded` оставила бы очевидную дыру: добавить инструмент вместо изменения |
| ошибка `Lock.Verify` | confirm | «не смогли проверить» — сигнал слабее, чем «изменилось», а под enforce его радиус поражения это весь сервер из-за одной кривой схемы |

Ошибочный путь `verifyTools` перестаёт быть голым `return`: `mismatched` очищается, `verifyErr` заполняется. Оставить старую карту — протухшие причины в одну сторону, молча очистить — в другую; «это не удалось проверить» единственный честный третий вариант.

**`internal/proxy/proxy.go`.** `Options`: убрать `Enforce`, добавить `Mode`. `Run`: событие `enforcement` сразу после `start`, баннер уровня на stderr, предупреждение если enforce включён без `--lock` и без `--policy` (сегодня это молчаливое ложное чувство безопасности), счётчики в событие `exit`. `startSweeper` дополнительно зовёт `g.expire`. `observer` при матче ответа на `initialize` фиксирует capabilities.

**`pump` не меняется.** Проверено: `back` это собственный stdout прокси, и неудачная запись туда означает, что клиент уже ушёл — возвращаться правильно, `serverIn.Close()` в вызывающем коде отработает на любом пути. Добавляется только событие `client-write-failed`, чтобы транскрипт объяснял, почему направление встало.

## Этап C — поверхность

**`cmd/mcp-guard/main.go`.** Логика выносится в чистые функции, чтобы тестировать без запуска бинарника:

```go
func off(getenv func(string) string) bool // 1|true|yes|on; MCPGUARD_OFF=0 НЕ снимает защиту
func resolveMode(f enforceFlag, p *policy.Policy) (policy.Mode, string)
func loadGuardConfig(lockPath, policyPath, rulesPath string, disabled bool) (...)
```

`MCPGUARD_OFF` проверяется **до открытия любого файла конфигурации** — в этом весь смысл: сегодня битая политика это `return 1`, то есть сервер не появляется в клиенте вовсе. Под выключателем локфайл, политика и правила не читаются, режим форсируется в observe, а неудача открытия лога понижается с `return 1` до предупреждения.

**Лог продолжает писаться.** Потерять запись именно той сессии, в которой охрана сглючила — противоположность полезного. Если проблема в самом логе, `-log-dir ""` уже есть.

Заметность, чтобы никто не остался без защиты молча: строка на stderr при старте, и событие `enforcement` с `from:"off"`, чтобы такую сессию можно было опознать в корпусе.

## Этап D — отчётность и документация

**`internal/eval/eval.go`** — `BlocksPerWeek` сейчас считает `Deny + Confirm` и после этих изменений сильно завышает дефолтный уровень. Заменяется на `BlocksPerWeekAt(m policy.Mode)`, `Report` печатает обе строки. Разница между ними и есть число, ради которого градация вводится. Сам `eval.Benign` остаётся независимым от режима — он пересчитывает вердикты офлайн из лога.

**`internal/replay/replay.go`** — capabilities в сводке; отказанные вызовы считаются отдельно; при коде `mcp.CodeBlocked` печатается `blocked`, а не `error -32000`.

**`internal/policy/policy.go`** — починка атрибуции при равной строгости: сегодня при `exec:deny` и `path:deny` в `Verdict.Rule` попадает `exec:<glob>`, хотя человеку нужно имя пути. Решение не меняется никогда, меняется только ярлык — но именно ярлык попадает в текст отказа и в гистограмму `eval`.

**Документация** — три уровня и правило комбинирования; аварийный выключатель; **переписать раздел «What `confirm` does today»**, который станет неверным в момент, когда это ляжет. Плюс задокументировать пробел с NFC-нормализацией путей в `internal/fspath` — он был сознательно пропущен, но нигде не записан.

## Проверка

Переиспользуются существующие механизмы: `drive`/`TestHelperMCPServer` из `internal/proxy/proxy_test.go` (тестовый бинарник переzапускается как MCP-сервер, сессия гоняется через `io.Pipe`).

Новое: `readEvents(t, logPath)` для проверок по событиям лога; `lockedBuffer` вместо `bytes.Buffer` для stderr (иначе `-race` на Linux упадёт: `os/exec` обслуживает его горутиной-копировщиком); файл `guard_internal_test.go` в пакете `proxy` — `pendingTools`, `mismatched`, `verifyErr` неэкспортируемые.

Ключевые тесты:

- **`TestEnforceRelaysConfirm`** — главный. Загрязнить сессию через `fetch_url`, записать `~/dev/build.sh` при `Mode: Enforce`. Ожидается: обычный ответ, сервер вызов увидел, в логе `policy-verdict` с `action:"confirm", blocked:false`.
- **`TestStrictBlocksConfirm`** — тот же сценарий при `Strict`: ошибка `-32000`, сервер не увидел ничего.
- **`TestEnforceStillBlocksDeny`** — запись в `~/.cursor/mcp.json` при `Enforce` блокируется.
- **`TestRefusedCallDoesNotLeakAnAttribution`**, **`TestAttributionsExpire`** — утечка карты, с инъекцией `now` и живой сессией на `SweepEvery: 5ms`.
- **`TestVerifyErrorClearsStaleMismatches`** — схема с дублирующимся ключом (её отвергает `canon.parseObject`): карта пуста, при `Enforce` пропускает, при `Strict` отказывает.
- **`TestRefusedCallIsInTheTranscript`** — `replay` печатает отказ и сообщает ноль «без ответа» и ноль в полёте.
- **`TestBatchIsGated`** и **`TestBatchRelayedByteForByte`** — дыра и её прозрачная половина.
- **`TestKillSwitchStartsWithBrokenPolicy`** — несуществующий и битый путь политики при `MCPGUARD_OFF=1` всё равно стартуют. Ровно то свойство, ради которого выключатель существует.
- **`TestEnforceFlagBare`** — `-enforce`, `-enforce=strict`, `-enforce=off`, и отлов `-enforce strict`.

Прогон целиком:

```powershell
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"; $env:CGO_ENABLED = "1"; go test -race ./...
```

Живая проверка после сборки: включить `-enforce` в конфиге Claude Desktop, попросить агента записать что-нибудь в `%USERPROFILE%\dev`, затем `mcp-guard replay` и `mcp-guard eval --benign ~/.mcp-guard/sessions` — обе строки «блокировок в неделю» должны появиться.

## Чего сознательно не делаем

- **Кэш «однажды подтверждено — впредь разрешать».** Очевидная следующая просьба, но ей нужна своя история доверия: где живёт, кто может писать, переживает ли правку политики. Отдельный дизайн, не довесок.
- **Переменная `MCPGUARD_ENFORCE`.** Три способа задать одно значение — на два больше нужного.
- **`elicitation/create`.** Клиент не объявляет поддержку; capabilities захватываются, чтобы к этому можно было вернуться с доказательствами.
- **HTTP/SSE, sandbox, LLM-классификатор** — этап 5 плана, помечен как опциональный.

## Известная цена

Смысл `mode: enforce` в файле политики меняется: вчера он блокировал confirm, завтра будет пропускать. Обнаружить намерение автора файла нельзя, поэтому смягчение только через заметность — событие `enforcement`, баннер при старте, README и текст коммита. На практике сейчас безболезненно: единственный существующий файл политики это встроенный дефолт с `mode: observe`.

Второе: под `strict` вместе с `--lock` одна кривая схема инструмента убивает сервер. Это осознанное следствие fail-closed на ошибках `Verify`, и оно заперто в `strict` именно поэтому.
